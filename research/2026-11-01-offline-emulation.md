# Offline synthetic entry-point emulation

## Scope and safety

`scripts/emulate_pe_entry.py` uses Unicorn 2.1.4 and pefile 2024.8.26 to interpret instructions from the preserved `Marathon.exe` in synthetic memory. It does **not** launch the executable, create a real thread, invoke a Windows API, or provide the emulated program network or OS services. It lazily maps bytes from the PE into emulator-owned pages, creates synthetic stacks and a minimal synthetic TEB, and stops before unmodeled interfaces. An optional mode patches standard-import slots only in emulator memory to inert markers. Results are model observations, not live-game traces; there is no claim that initialization or behavior would match Windows. The original executable is opened read-only.

## Reproducible observations

1. From the PE-declared entry point, with a synthetic stack/TEB and no import resolution, the model executes 6,060 instruction hooks and attempts an unmapped fetch at `0x335315a0`. Two runs matched in instruction count, stop, mapped pages, and recorded PCs (`entry-emulation-repeat.txt`).
2. The final indirect jump reads IAT slot `0x172c84418`; pefile identifies that standard import as `KERNEL32.dll!CreateThread` (`emulator-first-import.txt`). The on-disk IAT slot contains an unresolved loader value, explaining the synthetic-model stop. This is static import mapping plus a model trace, not an observed real API call.
3. With inert import markers, two equivalent runs stop before the `CreateThread` marker after 6,061 hooks, with synthetic thread-start argument `0x170814e10` and parameter pointer `0x7000001fef60`; they match in the recorded fields (`entry-import-emulation-repeat.txt`). The 47-byte range starting at RVA `0x30814e10` has a matching exception-table entry and statically decodes as a wrapper that calls another native function. It has not been executed on Windows or linked to Vault Breaker.
4. A deliberately synthetic follow-up starts that candidate with a fresh fake stack, zeroed integer registers, a shared fake TEB/memory image, and the captured synthetic parameter. It stops before an inert `VirtualProtect` marker after 198 hooks. Its modeled arguments specify address `0x172c84000`, length `0x8afa00`, and protection value `0x40`, corresponding to the PE's `.rdata` start and raw length. No protection is changed on the host.
5. In another model only, the harness simulates `VirtualProtect` returning success and writes an assumed previous protection value `2` into the fake thread stack. A one-million-instruction budget produces 2,424 one-byte writes in the emulated `.rdata` region, of which 2,409 changed the prior in-memory byte; zero read-before-write comparisons failed. The writes touched three pages and no `.text` writes were observed during this bounded phase. A repeat matched selected stops, counts, page counts and PC windows (`synthetic-thread-1m-repeat.txt`). With the API stub disabled, the control stops before the `.rdata` writes (`synthetic-thread-control.txt`). The budget was reached before a further external interface. This is evidence of a data-transforming initialization candidate under invented loader/API conditions, not proof of decryption, correctness, game startup, or the presence of Vault Breaker code.

Detailed model outputs and derived traces are private under `D:\Marathon-preservation\analysis`; concise summaries remain in `research/`. No memory dump or decrypted executable is claimed. The emulator sets all mapped image pages writable and executable to avoid modeling Windows memory protection; unsupported OS state, wrong return values, missing thread scheduling, self-modification semantics, exception handling, TLS and CPU behavior can alter the path. A successful model run must never be described as native execution.

## Reproduction

```powershell
$env:PYTHONPATH='D:\Marathon-preservation\tools\python'
$exe='D:\Marathon-preservation\build-26136895-20261031\Marathon.exe'
python scripts\emulate_pe_entry.py $exe --count 100000 --timeout-ms 30000 --intercept-imports --follow-thread
python scripts\emulate_pe_entry.py $exe --count 1000000 --timeout-ms 30000 --intercept-imports --follow-thread --stub-virtualprotect
```

The first command stops at the marker; the second simulates one or more successful `VirtualProtect` calls, up to eight, with the invented return behavior above. Both have explicit instruction and wall-time limits. The next investigation is to identify the transform and validate it using independent emulation or static analysis, while maintaining a strict separation between model output and evidence from an authentic offline process.

## XOR loop candidate

With the same synthetic one-million-instruction profile, all 2,424 recorded `.rdata` write hooks originated at VA `0x17004d61e` (file offset `0x3004cc1e`). Capstone decodes that address as `xor byte ptr [rdi], cl`; comparing each pre-write byte, the low byte of RCX, and Unicorn's reported write value matched the XOR relation in all 2,424 cases (`synthetic-thread-xor-summary.txt`). A trace of the 40 modeled PCs before the first write is retained privately in `D:\Marathon-preservation\analysis\synthetic-first-xor-preceding.txt`; it includes a byte-state update immediately before the write. This confirms the semantics of the observed synthetic writes, not the transform's complete algorithm or what the output means. Some writes do not change a byte, consistent with a zero XOR operand.

The PE exception directory contains a structurally plausible enclosing range RVA `0x3004d360`–`0x3004d655` (`synthetic-xor-function-entry.txt`); its validity is not established merely by its presence. A separate Ghidra `-noanalysis` attempt is importing the image and will restrict disassembly/decompilation to the corresponding VA range `0x17004d360`–`0x17004d654` using `scripts/ghidra/BoundedFunction.java`. Output is private in `D:\Marathon-preservation\ghidra-xor-attempt`; result pending. The range and prior stack/TEB/API behavior remain model assumptions, and the fact that the model reaches this code is not a live execution trace.

## Independent transform check

Capstone's static decode of the candidate function shows the AES substitution-table and round-constant byte patterns; the observed loop increments a 16-byte counter and XORs generated bytes into the destination. `scripts/compare_aes_reference.py` compares the privately captured synthetic-call inputs and write observations against PyCryptodome 4.2.0 AES-128 in counter mode, using a big-endian incrementing 128-bit counter. All 2,424 observed keystream bytes, output bytes and sequential destination addresses matched across 11 calls; ten calls were complete and the eleventh was observed only for its first 208 of 256 bytes (`synthetic-aes-reference-comparison.jsonl`). This is a verified equivalence for those synthetic inputs, not proof of the transform's role in authentic execution.

An experimental accelerated model replaces calls to the candidate routine with the independent AES reference and synthetic register/flag return values. On the first ten complete calls its input bytes and output hashes match the instruction-by-instruction model; the captured input contexts of the first eleven calls match (`accelerated-model-validation.txt`, `accelerated-model-context-validation.txt`). After that the accelerated path remains a hypothesis: it does not reproduce every possible side effect or prove identical native behavior. The 30-second pilot processed 1,962 such calls and 30,496 bytes before stopping; detailed output including synthetic inputs is private in `D:\Marathon-preservation\analysis\accelerated-pilot.json`. It does not execute the game or contact any service.

The first several completed modeled output regions include zeroed data and recognizable ordinary diagnostic text. This supports identifying the transformation as AES-128 counter mode for these sampled data, but does not establish that all `.rdata` or game code uses the same transformation, or that any output is Vault Breaker logic. No live credentials or running process were used.

The targeted Ghidra `-noanalysis` import completed: `BoundedFunction.java` reported disassembly and function creation for `0x17004d360`–`0x17004d654` and returned C-like pseudocode. The output also contains `Control flow encountered bad instruction data` and two `Bad instruction - Truncating control flow here` warnings, plus overlapping-global warnings. It is therefore a partial, potentially inaccurate reconstruction. Full output remains private in `D:\Marathon-preservation\ghidra-xor-attempt\stdout.txt` and `script.log`; the 2,424-byte AES reference match is independent of accepting this pseudocode as correct.

The accelerated model's private synthetic `.rdata` image has SHA-256 `e440e65ec21b63abf6edfd87868ab25d89946b54f8e53216a954eb62b7f10e42` and differs from the on-disk section at 6,963,199 bytes. It includes 544 deliberately patched inert IAT-marker slots and may contain untransformed data. A bounded ASCII/UTF-16 search (`synthetic-rdata-vault-search.jsonl`) found no exact selected Vault Breaker identifiers, but found ASCII `bungiescript` at section offset `0xa9370` and `script_workflow` matches. The string was absent in the prior raw-executable search. This is a new model-derived anchor, not evidence that script source or implementation is present, reachable, or authentic runtime memory.

### Unicorn VEX scalar-division fidelity defect

At 0x16188f698 the guest instruction bytes `c5 f2 5e f0` decode as `vdivss xmm6,xmm1,xmm0`; captured source operands are 1920.0f / 1080.0f. In an isolated Unicorn reproduction (`scripts/probe_unicorn_vdivss.py`, output `research/unicorn-vdivss-defect-validation.json`), keeping those sources fixed while changing the initial destination from 0 to 1920 changes the VEX result from 0 to 1.7777778. The equivalent SSE division yields float bits 0x3fe38e39. Thus this Unicorn build appears to use the old destination instead of the VEX first source for this instruction. This explains the previously observed zero divisor and casts doubt on prior synthetic traces using other scalar VEX arithmetic; it does not establish their exact impact or invalidate unrelated byte-verified records.

An opt-in hook corrects only instruction 0x16188f698 with exactly the observed source operands, sets the expected low result, copies the source's upper XMM lanes and clears upper YMM lanes. On replay it fired twice and the previous NaN/modff stop disappeared, reaching the same `SetWindowLongA` resolution (`tls-worker-vdivss-corrected.json`). This is a bounded correction, not a general AVX fix or native validation. The corrected branch retains all GUI/scheduler/Steam assumptions and no watched Cryo type read was observed. Session 2887 captures the style call. The NaN-propagating branch is superseded for this comparison and must not be treated as evidence of native arithmetic.
