# Sunrise architecture and Marathon message-row candidates

## Sources and scope

Project Sunrise's [architecture](https://projectsunrise.dev/docs/sunrise/architecture/) describes a Destiny 2-specific Steam API replacement, client hooks, local state and a local server. The client uses game-native functionality; an in-process HTTP handler and loopback BAP listener supply service behavior, with a separate service thread. Its documented egress guard redirects or refuses connections; it is not evidence that a Marathon build can safely be launched, or that an in-process guard alone can isolate an untrusted executable. Sunrise's [build notes](https://projectsunrise.dev/docs/destiny-2/the-build/) apply to Destiny 2 build 86657, not Marathon, and report different builds have different package formats, class sizes and protocols.

For Marathon, native Windows execution in an isolated copy with independently enforced network isolation could remove the need to approximate the CPU, GPU, scheduler and Windows APIs. It remains an untested prospect: the preserved client's startup, dependency and service requirements, anti-tamper behavior and compatible capture points must be established. No Marathon native process was launched here. A local Steam-facing compatibility layer and separately modeled service boundaries are architectural leads, not reusable protocol implementations or proof of Vault Breaker authority. The Sunrise [Activity Host](https://projectsunrise.dev/docs/destiny-2/activity-host-protocol/) splits authored activity state and peer simulation for its specific target; we have not verified the same split in Marathon.

## Candidate message records

Sunrise [describes](https://projectsunrise.dev/docs/destiny-2/behaviors/) 16-byte Destiny 2 class-message entries containing an eight-byte handler, four-byte message ID, and two two-byte fields. It identifies IDs `67774671` and `3088896a` as construct and destruct for that Destiny build. Using these as **search hypotheses**, `scripts/inspect_message_row_candidates.py` finds 472 and 1,790 respectively in 16-byte-aligned, file-backed rows of Marathon's synthetic `.rdata`. Of these, 471 and 1,567 respectively begin with an address in Marathon's code range; 224 have zero pointers. These matches and plausible shape are stronger than a string match, but they do not prove message semantics, function reachability, row boundaries, class ownership, or a slot dispatcher in Marathon. Counts cover only this reconstructed image and the selected two IDs. See `marathon-message-row-candidates.json` for digests and example rows.

At row VA `0x172d6da70`, the first qword is `0x170876740`, and the latter eight bytes decode to ID `67774671`, 16-bit values 2 and 0. The pointer qword is present in the original `.rdata`; the latter eight bytes are transformed. The reconstructed `.rdata` was separately replayed from the original with all 63,666 modeled transform events and verified against its saved digest (`analysis/message-row-rdata-replay.json`). For the specific latter eight bytes, event 14302's original native transform was run in an isolated Unicorn machine and matched both the reference and recorded output hash (`message-row-native-transform-validation.json`). This validates that transform on captured inputs, not the synthetic caller sequence or the whole image. Existing bounded Ghidra pseudocode at `0x170876740` and adjacent row's `0x16f6ffec0` shows calls into protected continuations, not useful function bodies. No link to any Vault Breaker class has been established.

A full synthetic-text disp32 scan against the three known shared-type object addresses and registry head produced one apparent match to object `0x1767faa80`, but its four displacement bytes cross `ret`/`int3` padding at `0x1718726ad`–`0x1718726b0`; it is not a demonstrated instruction. The one modeled registry-head hit corresponds to the already known initializer. Raw data is retained privately at `analysis/shared-registry-direct-displacements.json`; the scan cannot exclude indirect references or other code representations.

The most valuable next step is to locate the structures that own these candidate message arrays, connect them to a runtime class or serialized `{class, slot}` reference, and recover the code that indexes and invokes a row. Search and compare the surrounding data, relative pointers, protected continuations and method table initialization; verify candidate links with independent original-transform probes and bounded control flow. The current exact-name FNV search did not locate the 40 activity slot hashes in `.rdata`, so those names must not be assumed to be the IDs in these rows. If a native experiment is pursued, its isolation and startup dependencies need validation before starting the executable.

## Native arithmetic validation

`scripts/validate_native_scalar_avx.py` runs a fixed 13-byte generated arithmetic-only function on the local Windows CPU and the same arithmetic in Unicorn; it never executes Marathon bytes. Native `1920.0f / 1080.0f` yields `0x3fe38e39`, matching the narrowly scoped correction; Unicorn yields zero when the old destination is zero (`native-scalar-avx-validation.json`). This strengthens the isolated arithmetic conclusion, not the correctness of the entire modeled startup. The corrected checkpoint remains available, but its 1920x17 synthetic window result and additional uncorrected instructions mean it cannot support claims about real startup.
