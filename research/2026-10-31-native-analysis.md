# Native analysis attempt, 2026-10-31

Target: isolated `D:\Marathon-preservation\build-26136895-20261031\Marathon.exe`, 903,479,376 bytes, SHA-256 `d5c2fb538f4020a71060b553127259fcd5d3131beb89a4ec26a7d6ccfa9dfbfd`. REA opened this x86-64 PE and bound Ghidra 12.1.4. The request for pseudocode at `0x16f7a2690` (export `_setup_script_workflow_tag_suite`, previously identified RVA `0x2f7a2690`) timed out at the default 330,000 ms during whole-image startup. Ghidra reported large numbers of PE loading warnings, invalid import pointers and conflicting unwind data; the output was truncated. It reached auto-analysis but returned no completed analysis or pseudocode. A timeout is not proof the image cannot be analyzed. REA settings were then changed for the next startup to 1,200,000 ms and a second request started.

Using Capstone 5.0.9 on 128-byte windows in the same immutable snapshot, `export-disassembly.txt` shows an atypical sequence at the first export and invalid x64 decoding at the second export `run_script_workflow_tag_unit_tests__function`, mapped previously to file offset `0x2ef21d10` and VA `0x16ef22710`. Capstone is a linear disassembler, not a decompiler, and these bytes do not prove the exports implement Vault Breaker, explain the packing, or characterize executed memory. The package research notes already identify the names, byte offsets and the `.vmp0` section. No game code was executed or modified for this test.

The second request was ended by the MCP client call deadline after 450 seconds, before a REA result returned; this is distinct from the configured 1,200-second provider deadline. Following that client timeout, no associated Java process was visible and REA reported no observed active analysis, but no completed decompilation or retained result was obtained. Do not interpret the timeout as proof of failure for a longer CLI run.

A recursive filename search of the snapshot found no `.pdb`, `.map`, `.ilk`, or `.dbg` sidecar files. This is a filename-level observation, not proof that embedded symbols or debug information are absent. A small read-only PE export-table parser, `scripts/list_pe_exports.py`, examined 428 named exports in this exact executable. Case-insensitive substring search for `vault` or `encounter` returned no names; a search for `script` returned script-workflow unit-test symbols and unrelated `Description` matches. `inspect_pe_sections.py` recorded PE section sizes and entropy for at most the first 1 MiB of each raw section (`executable-sections.jsonl`). `.text` has 851,977,728 raw bytes; its first MiB measured 7.0692 bits/byte. This is bounded sampling, not a whole-section measurement, and high entropy does not distinguish compression from encryption or establish runtime behavior. The executable is much larger than the readable CIL helper.

A second bounded sampling pass reads 64 KiB every 16 MiB across `.text` (51 sampled windows, in `text-entropy-samples.jsonl`): two samples exceed 7.9 bits/byte and 44 are below 7, including all-zero samples. This is not whole-section coverage or a code/packing classification. Capstone linear decoding at two arbitrary, lower-entropy window offsets produced plausible x64 instructions that each include a direct jump to VA `0x162478533`; the target has interleaved short jumps and repeated register swaps (`sample-disassembly.txt`, `shared-jump-target-disassembly.txt`). These starts were sampled offsets, not established function entries; a linear disassembler can decode data or unreachable bytes, so these observations do not identify a function, reachable control flow, or Vault Breaker behavior. They do show why the whole section should not simply be described as uniform ciphertext. VA/file mapping used the `.text` section header and image base `0x140000000`.

## Declared program entry point

`pefile` identifies image base `0x140000000`, entry-point RVA `0x1a14e2b8`, and file offset `0x1a14d8b8` (`main-entrypoint.txt`). The independent section mapping agrees. Capstone decoding at that declared entry starts `push rbx`, a no-op, and an instruction at VA `0x15a14e2c2` spanning bytes through `0x15a14e2c5`. The direct call at `0x15a14e2cc` targets `0x15a14e2c4`, inside that previous instruction; decoding from the target yields a jump to `0x15a14e2ed`. These overlapping streams and the subsequent direct jumps are visible in `main-entrypoint-disassembly.txt`, `entrypoint-call-target.txt`, and `entrypoint-jump-target.txt`; use `scripts/disassemble_text_windows.py` with the recorded offsets to reproduce. This is static evidence of overlapping x64 decoding at a PE-declared entry and helps explain why linear disassembly is insufficient. It does not establish what happens in a running process, the protection scheme, or a path to Vault Breaker logic.

A bounded Capstone-based graph walker (`scripts/trace_pe_flow.py`) starts at the declared entry, decodes each address independently, and preserves the overlapping call target instead of forcing one linear instruction stream. With a 100-address limit it wrote `D:\Marathon-preservation\analysis\entrypoint-flow.jsonl` and stopped with four queued addresses. The graph records direct branches and conservative call fallthrough as static possibilities; it does not emulate registers, stack effects, indirect jumps, or execution, and its reachable set is incomplete. The build-specific `.text` mapping and Capstone 5.0.9 are explicit dependencies. This is disassembly, not decompiled game logic; keep its game-derived output private.

The seeded profile timed out at 600,000 ms with no pseudocode; the completed error record is `D:\Marathon-preservation\native-export-seeded.json`. The earlier seed report still independently records the target as undecodable before auto-analysis. A larger static instruction-graph pass with a 5,000-address cap produced `D:\Marathon-preservation\analysis\entrypoint-flow-5000.jsonl`; it exhausted its cap with 318 queued addresses. Its conservative paths, especially fallthrough after calls and both conditional-branch edges, may include unreachable bytes. It cannot recover execution, semantics, or game logic; summary counts are in `entrypoint-flow-5000-summary.txt`.

## Bounded no-autoanalysis attempt

A separate local Ghidra headless experiment uses `-noanalysis` and `scripts/ghidra/EntrySlice.java` to attempt disassembly and decompilation only within entry VA range `0x15a14e2b8`–`0x15a14e2d0`. That is an artificial slice that excludes the overlapping alternate target's full flow and cannot represent the program's complete behavior. Two initial starts failed during Ghidra's Java/Felix cache initialization before target import; a third process uses task-local `APPDATA`, `LOCALAPPDATA`, Java home and temporary paths. Its logs are retained as `D:\Marathon-preservation\entry-slice-c-*.txt` and `entry-slice-c-ghidra.log`; result pending. This does not execute or modify the game.
Within the 5,000-address overapproximate graph, a static pattern count found seven adjacent pairs of identical `xchg` instructions and one direct jump to its immediately following instruction (`entry-graph-pattern-summary.txt`). This counts decoded graph nodes, including potentially unreachable paths, and is not a safe program simplification or proof of observed execution. The full graph stays outside the repository.

The bounded `-noanalysis` experiment completed on the third, task-isolated startup. Ghidra imported the preserved executable read-only, disassembled the explicitly bounded VA range, created an artificial `entry_slice`, and returned pseudocode. Its output explicitly warns `Call to offcut address within same function` and `Bad instruction - Truncating control flow here`. The generated C represents a truncated, artificial analysis slice and must not be interpreted as recovered program behavior. Logs and output: `D:\Marathon-preservation\entry-slice-c-stdout.txt`, `entry-slice-c-script.log`, `entry-slice-c-ghidra.log`. The original executable was not modified. This directly tests why a simple Ghidra decompile does not faithfully handle the overlapping entry path; it does not prove that every native function is inaccessible.

## Exact on-disk identifier searches

`scripts/find_pe_tag_bytes.py` searched the entire snapshot `Marathon.exe` for the 11 selected little-endian four-byte tag or class IDs in `native-tag-byte-matches.jsonl`; all returned zero hits with no truncation. It separately searched six 32-bit FNV-1 name-hash candidates in `native-name-hash-byte-matches.jsonl`, also with zero hits. `sc_handle_create` produces `D793488F`, agreeing with the previously verified metadata example; the remaining hashes are search candidates, not proof the runtime uses those values. The search does not cover transformed IDs, other hash algorithms, indirection, loaded/decrypted memory, package code, or remote services. It neither proves the selected implementation is absent nor identifies its location.

Reproduce with `python scripts/find_pe_tag_bytes.py <snapshot-exe> <hex-id>...` and `python scripts/fnv1_candidates.py <name>...`. The search uses a read-only memory map and does not launch the game.
