## 1. Executive Summary

This investigation analyzed the Bungie Access Protocol (BAP) Service 304/305 certificate exchange blocker in Marathon Build 26136895. Building upon the root cause established in `MARATHON_STEAM_CERT_BAP_ROOT_CAUSE.md`, we conducted static binary analysis, Unicorn engine emulation, memory dump inspection, and protocol auditing to recover the exact Service 305 contract, evaluate the certificate trust boundary, rectify independent local server deficiencies, and establish the next preservation milestone.

### Key Discoveries & Implementation Milestones:

1. **Exact Schema Recovered from Embedded Binary Descriptor [VERIFIED]:**  
   We extracted the compiled `FileDescriptorProto` directly from the retail executable (`.rdata` offset `0x3a7252`, RVA `0x3302b252`, `steamnetworkingsockets_messages_certs.proto`). The exact schema for `CMsgSteamDatagramCertificate`, `CMsgSteamDatagramCertificateSigned`, and `CMsgSteamDatagramCertificateRequest` was recovered without speculation.
2. **GameNetworkingSockets Trust Boundary Demarcation [VERIFIED]:**  
   Targeted analysis of `ISteamNetworkingSockets::SetCertificate` (RVA `0x30154670`) and its underlying implementation (`csteamnetworkingsockets.cpp` / `.rdata` string at RVA `0x33028e40`) revealed a critical architectural insight:
   - GameNetworkingSockets **does not reject an unverified certificate authority on the local client**. If `CertStore_CheckCert` fails, it logs:  
     `"SetCertificate: We are not currently able to verify our own cert! %s. Continuing anyway!"`  
     and **continues execution**.
   - What it **does** enforce strictly are identity and key constraints:
     - `key_data` must match the ephemeral Ed25519 public key generated by the client in Service 304.
     - `legacy_steam_id` / `identity_string` must match the local user identity (`76561198000001001`).
     - `app_ids` must include `3065800`.
     - Valid time bounds (`time_created` <= current_time <= `time_expiry`).
3. **Severe Local Server Implementation Deficiencies Identified [VERIFIED]:**  
   The previous `marathon_server.py` implementation suffered from four independent architectural defects:
   - **Abrupt Socket Teardown:** The server unconditionally tore down the TCP connection on Status 503 (`if status != BAP_STATUS_OK: return`), preventing the client from maintaining its BAP session.
   - **Hardcoded Post-305 Abort:** Even on Status 200, the server executed `if sent_ssc: return`, unconditionally closing the connection on the very next client frame.
   - **Nonce Destruction / Single-Shot Framing:** `BapChannel.seal_first_response` wiped `self.send_nonce = b""` and had no nonce sequence advancement, breaking AES-GCM decryption for any subsequent authenticated frames.
   - **Unauthenticated Type-1 Routing Block:** Non-304 frames received inside encrypted Type-1 outer frames triggered an immediate return.
4. **Local Implementation & Verification Complete [VERIFIED]:**  
   We implemented:
   - Fixed-width protobuf types (`fixed32` / `fixed64`) in `scripts/marathon_protobuf.py`.
   - Structured Service 304 parsing and Service 305 encoding/decoding in `scripts/marathon_ssc.py`.
   - Nonce evolution (`advance_bap_nonce`) and bidirectional multi-frame authenticated AES-128-GCM sessions in `scripts/marathon_server.py`.
   - 10 comprehensive unit tests in `tests/test_bap_service_305.py` and native binary Unicorn emulation verification of decoder `0x30A3F910`. All 28 tests across the project test suite pass cleanly.

## 2. Phase 1: Verified Service 305 Wire Contract & Protobuf Schema

### 2.1 The Wire Protocol Envelope

A BAP Service 305 response is transmitted as an encrypted inner response wrapped in an authenticated outer frame:

```
+-----------------------------------------------------------------------------------------+
|                                    BAP Outer Frame                                      |
|  Magic (1B): 0x01 | Frame Type (1B): 0x01 (GCM) | Payload Length (4B, BE): 16 + N      |
+-----------------------------------------------------------------------------------------+
|                                 Authenticated Payload                                    |
|  AES-GCM Auth Tag (16B) | AES-128-GCM Ciphertext (N Bytes)                              |
+-----------------------------------------------------------------------------------------+
|                               Decrypted Inner Response Body                             |
|  Service ID (2B, BE): 305 (0x0131) | Task ID (4B, BE): Echo from request (e.g. 2)     |
|  Status Code (2B, BE): 200 (0x00C8) | Protobuf Body (N - 8 Bytes)                       |
+-----------------------------------------------------------------------------------------+
```

## 3. Phase 2: Certificate Trust Boundary & Installation Analysis

### 3.1 Trace of Execution Flow from BAP to Engine

1. **Status Code Check (`0x2FA1FC46`):**  
   The callback inspects the inner BAP header status:
   ```x86asm
   0x16fa1fc46: mov  eax, 0xc8                  ; 200 OK
   0x16fa1fc4b: cmp  word ptr [rsp + 0x30], ax  ; Must equal 200
   ```
   If status is non-200 (e.g. 503), the callback exits immediately. The certificate payload is neither parsed nor installed.

2. **Protobuf Decoding (`0x30A3F910`):**  
   The decoder verifies tag `0x1A` (Field 3, wire type 2) and validates `length <= 2048`. On success, it returns an 8-byte length prefix followed by the decoded container bytes in the caller's output buffer, returning `AL = 1`.

3. **Certificate Dispatcher (`0x2FADAD10`):**  
   At RVA `0x2FADAD10`, the dispatcher reads the 16-bit decoded length at `[rdx]` and invokes Marathon's internal certificate installer:
   ```x86asm
   0x16fadad3d: movzx edx, word ptr [rdx]       ; Cert byte length (Arg 2)
   0x16fadad40: call  0x170154670               ; Marathon SetCertificate
   0x16fadad45: test  al, al                    ; Check boolean result
   0x16fadad47: je    0x16fadad7d               ; Branch to failure log if false
   0x16fadad49: call  0x149e66bbe               ; Success path: mark certificate ready
   ```
   If `al == 0`, dispatcher calls `0x305752A0` (`0x1705752a0`), logging:  
   `"networking:server:bap:protocol_source: failed to set signed steam certificate"`.

4. **Internal `SetCertificate` (`CSteamNetworkingSockets::InternalSetCertificate` at RVA `0x30154670`):**  
   Static strings recovered at RVA `0x33028de8` - `0x33028e40` prove that Marathon incorporates Valve's `GameNetworkingSockets` engine code. In `InternalSetCertificate`:
   - `msgCertSigned.ParseFromArray(pCertificate, cbCertificate)`: Fails if container protobuf is invalid (`"CMsgSteamDatagramCertificateSigned failed protobuf parse"`).
   - `SteamNetworkingIdentityFromCert`: Checks identity match (`"Cert is for identity '%s'. We are '%s'"`).
   - Public Key Match: Compares `key_data` from cert with the ephemeral public key generated by the client (`"Cert public key does not match our private key"`).
   - AppID Authorization: Verifies `app_ids` contains `3065800` (`"Cert does not authorize us for App %u"`).
   - **CA Signature Validation (`CertStore_CheckCert`):**  
     ```cpp
     const CertAuthScope *pAuthScope = CertStore_CheckCert( msgCertSigned, msgCert, authTime, errMsg );
     if ( !pAuthScope ) {
         SpewWarning( "SetCertificate: We are not currently able to verify our own cert! %s. Continuing anyway!", errMsg );
     }
     ```
     **Crucial Finding:** When a client installs its own certificate, an untrusted or missing CA signature produces only a warning and does **not** fail `SetCertificate`. The client process accepts the certificate and transitions `GetAuthenticationStatus` (`0x32B2A220`, slot `0xA8`) to `100` (`k_ESteamNetworkingAvailability_Current`).
   - Downstream limitation: Although the client accepts the certificate locally, when it subsequently connects to a remote relay, the remote relay checks the CA signature against Valve's master CA. In our offline environment, the local server hosts the relay, eliminating external verification hurdles.

## 4. Phase 3: Backend Audit Findings & Deficiencies Corrected

| Area | Prior Implementation Defect | Consequence | Implemented Resolution |
|---|---|---|---|
| **SSC Request Lookup** | Keyed by SHA-256 of entire request body (`hashlib.sha256(request.payload).hexdigest()`). | Since the client generates a fresh ephemeral Ed25519 key on every boot, the hash was never predictable, guaranteeing 503 cache misses. | Added `parse_ssc_request` in `marathon_ssc.py` to inspect the client's ephemeral public key and identity dynamically. |
| **Response on Missing Cert** | Returned 503 and immediately closed the TCP socket (`if status != BAP_STATUS_OK: return`). | Prematurely severed the client's BAP connection; client was unable to receive keepalives or future activity frames. | Removed forced socket closure; connection remains open with diagnostic logging. |
| **Post-305 Processing** | Executed `if sent_ssc: return` upon receiving any frame after Service 305. | Guaranteed immediate disconnection as soon as the client acknowledged the certificate or sent Service 6. | Removed `sent_ssc` hard abort; post-305 frames continue in the message loop. |
| **Cryptographic Nonce Evolution** | Single-shot `send_nonce = b""`; `receive_nonce` never updated. | Second authenticated frame caused `ValueError` or GCM auth tag mismatch (`InvalidTag`). | Implemented `advance_bap_nonce` (little-endian counter semantics) for both send and receive streams. |
| **Encrypted Service Routing** | Handled only Service 304 under `frame_type == 1`; all other services returned immediately. | Legitimate post-305 activity requests (Service 6, 18, 250) could never be decrypted or dispatched. | Routed all authenticated type-1 frames through `channel.open_frame()` and `server_instance.dispatch_bap_request()`. |

## 5. Phase 4: Implementation Changes & Code References

### 5.1 `scripts/marathon_protobuf.py`
- Added support for `WIRE_FIXED64 = 1` and `WIRE_FIXED32 = 5`.
- Implemented `ProtobufWriter.fixed64(field_number, value)` and `ProtobufWriter.fixed32(field_number, value)` using little-endian binary serialization (`struct.pack("<Q", value)` and `struct.pack("<I", value)`).
- Extended `ProtobufReader.parse()` to decode fixed64 and fixed32 fields without raising `NotImplementedError`.

### 5.2 `scripts/marathon_ssc.py` (New Module)
- Created dedicated codec and validator implementing:
  - `parse_ssc_request`: Parses Service 304 wire payloads, extracts ephemeral Ed25519 public keys, Steam IDs, and App IDs, and validates nested CSR structures.
  - `build_inner_certificate`: Builds `CMsgSteamDatagramCertificate` conforming to Marathon's recovered schema.
  - `build_signed_certificate_container`: Wraps inner certificates inside `CMsgSteamDatagramCertificateSigned`.
  - `build_synthetic_ssc_response`: Generates complete Service 305 wire bodies for offline testing (explicitly labeled as non-production test fixtures).
  - `parse_ssc_response`: Decodes and validates Service 305 response bodies.

### 5.3 `scripts/marathon_server.py`
- Added `advance_bap_nonce(nonce: bytes) -> bytes`: Increments the 64-bit invocation counter in the first 8 bytes of the 12-byte nonce in little-endian order, preserving directional flags.
- Enhanced `BapChannel`:
  - `open_frame(payload: bytes) -> BapRequest`: Decrypts incoming AES-128-GCM frames and advances `receive_nonce`.
  - `seal_response(service_id, task_id, status, body) -> bytes`: Encrypts inner responses and advances `send_nonce`.
  - `seal_request(service_id, task_id, payload) -> bytes`: Encrypts inner requests and advances `send_nonce`.
  - Retained `open_first_frame` and `seal_first_response` as backward-compatible wrappers.
- Updated `MarathonServer`:
  - Added `--allow-synthetic-ssc` CLI flag and `allow_synthetic_ssc: bool` option.
  - In `ssc_response()`: checks provisioned response directory first; if absent and `allow_synthetic_ssc` is enabled, generates a dynamic synthetic response matching the client's ephemeral public key; otherwise cleanly returns Status 503 with explicit diagnostic logging.
- Refactored `handle_bap_connection`:
  - Preserves persistent socket connections across multiple authenticated Type-1 frames.
  - Emits detailed metadata logs for incoming Service 304 requests.
  - Handles non-304 authenticated requests through the standard dispatch engine.

## 7. Evaluation of Preservation Paths (Phase 5)

We evaluated the four potential preservation paths defined in the mission brief:

- **Path A: Existing response material is sufficient**  
  **Evaluation: REJECTED.** Because the client generates a fresh ephemeral Ed25519 key pair on every launch, no static pre-recorded certificate can satisfy the client's internal check (`"Cert public key does not match our private key"`).
- **Path B: Local protocol implementation is incomplete**  
  **Evaluation: CONFIRMED & RESOLVED.** The server contained severe protocol framing, nonce advancement, and lifecycle bugs. These have now been resolved and validated.
- **Path C: Genuine Steam/Bungie signing dependency remains**  
  **Evaluation: QUALIFIED.** For client-side certificate installation (`SetCertificate`), the engine does **not** hard-block on an untrusted CA signature (it logs `"Continuing anyway!"`). However, for downstream relay routing and peer connectivity, Valve/Bungie CA signing would normally be validated by remote nodes.
- **Path D: Further Tiger-engine reconstruction is necessary**  
  **Evaluation: CONFIRMED FOR GAMEPLAY READINESS.** Because the preservation environment hosts both client and server locally, pairing our corrected Service 305 backend with an offline proxy fallback (hooking `0x30154670` to force `al = 1` and vtable slot `0xA8` to return `100` / `k_ESteamNetworkingAvailability_Current`, identical to Project Dawn) provides a complete, resilient solution.
